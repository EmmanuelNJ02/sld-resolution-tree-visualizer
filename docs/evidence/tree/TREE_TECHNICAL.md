## 2. Purpose and Scope

Part A (Emmanuel Nunez Jimenez) resolves a query and returns a **flat, chronological list** of resolution events (`step/8`). That list says what happened, in order, but it does not say which event belongs to which node, who is the parent of whom, or whether a whole branch led to a solution.

Part B turns that list into an **SLD tree** and exports it as **JSON** for the web visualizer of Part C (Keynell Molina Mora).

```text
Part A                         Part B (this component)                 Part C
sld_trace/4  --step/8 list-->  build_tree/2 --node/9 list-->  JSON  --> browser
                               export_tree_json/3
```

### Individual responsibility

1. Register the goals, applied clauses and substitutions of each resolution step.
2. Organize the steps into nodes with parent-child relationships.
3. Identify successful, failed and depth-limited (cutoff) branches, including inner nodes.
4. Export the tree to a documented JSON format.
5. Test the component individually and integrated with Part A.

### Outside this component

- SLD resolution, unification and clause selection (Part A).
- Drawing the tree in the browser (Part C).

## 4. Input: the Steps of Part A

Each event produced by `sld_trace/4` has the form:

```prolog
step(Sequence, Path, Depth, Action, Goal, Clause, RemainingGoals, Bindings)
```

Observed output for `(parent(ana, X), parent(X, diego))` with depth 3:

| Seq | Path | Depth | Action | Goal | Clause | X |
|---:|---|---:|---|---|---|---|
| 1 | `[]` | 0 | `start` | `parent(ana,A),parent(A,diego)` | — | `_` |
| 2 | `[1]` | 1 | `apply` | `parent(ana,A)` | `parent(ana,luis)` | luis |
| 3 | `[1]` | 1 | `failure` | `parent(luis,diego)` | — | luis |
| 4 | `[]` | 0 | `backtrack` | `parent(ana,A)` | — | `_` |
| 5 | `[2]` | 1 | `apply` | `parent(ana,A)` | `parent(ana,marta)` | marta |
| 6 | `[2,1]` | 2 | `apply` | `parent(marta,diego)` | `parent(marta,diego)` | marta |
| 7 | `[2,1]` | 2 | `success` | — | — | marta |

Key observations that drive the design:

1. **Only `start` and `apply` create nodes.** `start` creates the root; every `apply` creates a child.
2. **`success`, `failure` and `cutoff` do not create nodes:** they report the outcome of the node that has the same `Path`.
3. **`backtrack` does not create anything:** it only means that the next `apply` is a sibling. In the tree this is already visible as a new child of the same parent.
4. **The `Path` is the address of a node.** `[2, 1]` means "second alternative at the root, then first alternative". Every `apply` extends the path of its parent by one position, so **the parent of a path is the same path without its last element**.

## 5. Output: the Tree Representation

`build_tree/2` returns a list of nodes:

```prolog
node(Id, ParentId, Path, Depth, Goal, Clause, Pending, Bindings, Status)
```

| Field | Content | Source |
|---|---|---|
| `Id` | `n0`, `n1`, ... in creation order | generated by Part B |
| `ParentId` | `Id` of the parent; `none` for the root | computed from `Path` |
| `Path`, `Depth` | address and depth of the node | copied from the step |
| `Goal` | root: the query; other nodes: goal resolved to reach the node | copied from the step |
| `Clause` | clause applied to reach the node; `none` for the root | copied from the step |
| `Pending` | goals that remain at this node | copied from the step |
| `Bindings` | values of the query variables at this node | copied from the step |
| `Status` | `success`, `failure` or `cutoff` | computed by Part B (section 7) |

An `apply` step describes two things at once: the **edge** from the parent (`Goal` resolved with `Clause`) and the **new node** (its `Pending` goals and `Bindings`). The node stores both, so no separate edge list is needed.

Result for the example above:

```text
n0  []      parent(ana,A),parent(A,diego)       success
├── n1  [1]     via parent(ana,luis)    pending: parent(luis,diego)   failure
└── n2  [2]     via parent(ana,marta)   pending: parent(marta,diego)  success
    └── n3  [2,1]   via parent(marta,diego)  pending: (none)         success
```

## 6. Tree Construction Design

`build_tree/2` is a pipeline of three stages. Each stage has one responsibility and produces a richer representation of the nodes:

```prolog
build_tree(Steps, Nodes) :-
    raw_nodes(Steps, RawNodes),                         % 6.2  create and name the nodes
    link_nodes(RawNodes, Linked),                       % 6.3  connect each node to its parent
    maplist(complete_node(Linked, Steps), Linked, Nodes).  % 7  add the branch status
```

```text
step/8  --raw_nodes-->  raw/7  --link_nodes-->  linked/8  --complete_node-->  node/9
```

### 6.1. Parent path

```prolog
parent_path(Path, ParentPath) :-
    append(ParentPath, [_], Path),
    !.
```

`append/3` is used in reverse to **split** the path into two parts, where the second part must be a list of exactly one element (`[_]`). The first part is the parent path:

| `Path` | Split | `ParentPath` |
|---|---|---|
| `[2, 1]` | `[2] + [1]` | `[2]` |
| `[2]` | `[] + [2]` | `[]` |
| `[]` | impossible | fails |

The root fails without a special case: the empty list cannot be split leaving one element on the right. In logic programming the failure itself is the answer: the root has no parent. The cut makes the predicate deterministic (there is only one valid split).

### 6.2. Node creation

```prolog
creates_node(step(_, _, _, start, _, _, _, _)).
creates_node(step(_, _, _, apply, _, _, _, _)).

raw_nodes(Steps, RawNodes) :-
    include(creates_node, Steps, NodeSteps),
    number_nodes(NodeSteps, 0, RawNodes).
```

- `creates_node/1` is a filter implemented by **unification**: a step matches one of the two facts only if its fourth field is `start` or `apply`.
- `include/3` keeps the steps that satisfy the filter (the equivalent of `filter` in JavaScript or Java streams).
- `number_nodes/3` walks the filtered list with a counter and builds `raw(Id, Path, Depth, Goal, Clause, Pending, Bindings)`, where `atom_concat(n, N, Id)` produces `n0`, `n1`, ...

`number_nodes/3` is **tail recursive**: the recursive call is the last goal, the counter acts as an accumulator, and the output list is built with an open tail (the head `raw(...)` is placed before the recursive call fills the rest).

### 6.3. Parent-child relationships

```prolog
find_parent_id([], _, none) :- !.
find_parent_id(Path, RawNodes, ParentId) :-
    parent_path(Path, ParentPath),
    member(raw(ParentId, ParentPath, _, _, _, _, _), RawNodes),
    !.

link_nodes(RawNodes, LinkedNodes) :-
    maplist(link_node(RawNodes), RawNodes, LinkedNodes).
```

- The root's parent is `none`.
- For any other node, the parent path is computed and `member/2` searches, by unification, the node whose second field is that path. The search always succeeds because Part A explores depth-first: a parent is always created before its children.
- `link_node/3` copies a `raw/7` node into a `linked/8` node with the parent identifier as an extra field.
- `maplist(link_node(RawNodes), ...)` uses **partial application**: `link_node/3` receives the full list as its first argument (needed to search the parent), and `maplist` adds the input and output nodes.

## 7. Branch Status

Part A only reports the outcome of **leaf** nodes. Its contract states that the outcome of higher-level nodes must be inferred by Part B. The rule is:

| Children statuses | Node status |
|---|---|
| at least one `success` | `success` |
| no `success`, at least one `cutoff` | `cutoff` |
| only `failure` | `failure` |

```prolog
terminal_action(success).
terminal_action(failure).
terminal_action(cutoff).

terminal_outcome(Path, Steps, Outcome) :-
    member(step(_, Path, _, Outcome, _, _, _, _), Steps),
    terminal_action(Outcome),
    !.
terminal_outcome(_, _, none).

combine_status(Statuses, success) :- member(success, Statuses), !.
combine_status(Statuses, cutoff)  :- member(cutoff, Statuses), !.
combine_status(_, failure).

branch_status(Id, Path, Linked, Steps, Status) :-
    terminal_outcome(Path, Steps, Outcome),
    (   Outcome \== none
    ->  Status = Outcome
    ;   findall(ChildStatus,
                (   member(linked(ChildId, Id, ChildPath, _, _, _, _, _), Linked),
                    branch_status(ChildId, ChildPath, Linked, Steps, ChildStatus)
                ),
                ChildStatuses),
        combine_status(ChildStatuses, Status)
    ).
```

- `terminal_outcome/3` looks for a terminal step with the same `Path`. `terminal_action/1` discards the `apply` and `backtrack` steps that share the path. If there is none, the node is not a leaf (`none`).
- `combine_status/3` applies the priority `success > cutoff > failure`. The cuts prevent lower-priority answers on backtracking.
- `branch_status/5` is a **recursive tree visitor**: on leaves it answers directly (base case); on inner nodes it finds the children (nodes whose parent field is `Id`), computes their status recursively and combines the results.

Trace for the root of the example:

```text
branch_status(n0)                    terminal? none -> children n1, n2
├── branch_status(n1)                terminal: failure
├── branch_status(n2)                terminal? none -> child n3
│   └── branch_status(n3)            terminal: success
│   combine([success])          -> success
combine([failure, success])     -> success
```

With this rule the whole path from the root to each solution is marked `success`, so the visualizer can highlight it, and `cutoff` is never confused with `failure`.

## 8. JSON Export

### 8.1. Public predicates

```prolog
print_tree_json(+Query, +MaxDepth)          % prints the JSON on the screen
export_tree_json(+Query, +MaxDepth, +File)  % writes the JSON to a file
write_tree_json(+Stream, +MaxDepth, +Nodes, +Answers)
```

`print_tree_json/2` and `export_tree_json/3` run the complete chain: `sld_trace/4` (Part A) → `build_tree/2` → `write_tree_json/4`. The JSON format is specified in `docs/TREE_JSON_FORMAT.md`.

### 8.2. Design decision: manual writer

SWI-Prolog provides `library(http/json)`, which was not covered in the course. The main exporter writes the JSON **manually** with `format/3` and `write/2`, so that every part of the output is explained with course techniques:

| JSON problem | Solution | Technique |
|---|---|---|
| Quotes inside texts | `escape_codes/2` walks the text as a list of character codes and inserts `\` before `"` and `\` | lists of codes (as in DCGs), tail recursion |
| Commas between elements, not after the last one | `write_items/4`, with cases for empty, one and several elements | recursion over lists |
| One writer for texts, ids, bindings and nodes | `write_items/4` receives the writer predicate and calls it with `call/3` | higher-order predicates, combinators |
| `none` → `null` | special clause with cut in `json_text/2` and `json_id/2` | unification, cut |
| Children of each node | `findall/3` of the nodes whose parent is the node | metapredicates |
| Answer → node | `member/2` of the node with the answer's path | unification |

```prolog
write_items(_, _, [], _).
write_items(Stream, Writer, [Item], _) :-
    !,
    call(Writer, Stream, Item).
write_items(Stream, Writer, [Item | Rest], Separator) :-
    call(Writer, Stream, Item),
    write(Stream, Separator),
    write_items(Stream, Writer, Rest, Separator).
```

`write_items/4` does not know what it writes; it is a combinator, like `star`/`plus` in DCG parsers. The same predicate writes lists of texts (`json_text`), identifiers (`json_id`), bindings (`json_binding`), nodes (`json_node(Nodes)`) and answers (`json_answer(Nodes)`); the last two use partial application to pass the node list.

### 8.3. Alternative: `library(http/json)`

For comparison, the module also provides `print_tree_json_lib/2`, `export_tree_json_lib/3` and `write_tree_json_lib/4`. They convert each node into a SWI-Prolog **dict** (`node_dict/3`, `binding_dict/2`, `answer_dict/3`, `tree_dict/4`, mostly with `maplist/3`) and write it with `json_write_dict/2`.

| | Manual writer (main) | Library (alternative) |
|---|---|---|
| Course techniques | all | dicts; `json_write_dict/2` is a black box |
| Escaping and commas | controlled by the component | done by the library |
| Field order | as documented | alphabetical (dicts are ordered by key) |
| Code size | larger | smaller |

Both produce the same data. The manual writer is the one used by the examples, the tests and Part C. The library is used in the integration tests only as an **independent validator**: if `json_read_dict/2` can read the file, the JSON is valid.

## 11. Known Limitations

1. **Dependency on the Part A format.** The component relies on the `step/8` structure and on paths being unique per node, as documented in `docs/ENGINE_INTERFACE.md`.
2. **Texts, not terms.** Goals, clauses and bindings are the text snapshots produced by Part A; the component does not inspect or re-unify Prolog terms.
3. **Derived status.** The status of an inner node summarizes its subtree. A `success` node can have `failure` or `cutoff` children; the visualizer should use each node's own status to color it.
4. **`cutoff` is not falsity.** A `cutoff` branch might have succeeded with a larger depth limit.
5. **Escaping.** `escape_codes/2` escapes `"` and `\`. Control characters (for example a line break inside a quoted atom) are not escaped; they do not occur in the example programs.
6. **Efficiency.** Parent and child lookups use `member/2` over the node list, so construction is quadratic in the number of nodes. This is adequate for the educational tree sizes of the project.
7. **Files.** `export_tree_json/3` overwrites the target file if it exists.

## 12. Integration

- **With Part A:** consumes `sld_trace/4` exactly as documented in `docs/ENGINE_INTERFACE.md` (`step/8`, `answer/2`, `none`, string snapshots, `failure` vs `cutoff`, `backtrack` as return to an existing parent). Verified by the integration tests.
- **With Part C:** produces the format defined in `docs/TREE_JSON_FORMAT.md`; six example files are available in `examples/json/`.

## 13. Demonstration Guide

1. **Introduce the contribution:** Part A returns a flat list of events; Part B builds the tree and exports JSON.
2. **Show the input:** run `sld_trace/4` for `(parent(ana, X), parent(X, diego))` and explain the 7 steps (section 4).
3. **Show the tree:** run `build_tree/2` on those steps; explain node ids, parent ids and paths.
4. **Explain the parent rule:** `parent_path([2,1], P)` and why `parent_path([], P)` fails.
5. **Explain the status:** leaves from Part A, inner nodes by the visitor `branch_status/5`; compare `parent(diego, X)` (failure) with `endless` (cutoff).
6. **Show the JSON:** `print_tree_json/2`; point out `null`, `children` and `answers`.
7. **Run the tests:** the combined command (54/54).
8. **Close with limitations** (section 11).
