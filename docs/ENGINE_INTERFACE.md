## 1. Purpose

This document defines the proposed interface between the SLD resolution engine developed by Emmanuel (Part A) and the SLD tree construction module developed by Roy (Part B).

The engine is responsible for resolving Prolog queries and producing basic information about the resolution process.

The tree construction module is responsible for recording and organizing that information into an SLD resolution tree and exporting it as JSON.

The interface must allow the components to work independently while preserving the information required for their integration.

## 3. Proposed Engine Interface

The proposed public predicate is:

```prolog
sld_trace(+Query, +MaxDepth, -Steps, -Answers).
```

### Parameters

**Query**

The Prolog query to resolve.

The query must belong to the supported language subset.

**MaxDepth**

A non-negative integer defining the maximum resolution depth.

Depth counts clause-resolution steps, beginning at zero.

**Steps**

An ordered list containing basic information about the resolution process.

These steps will be consumed by Part B to construct the SLD tree.

**Answers**

A list of the solutions found, including substitutions for the original query variables.

The final predicate signature and exact data representations must be validated between Parts A and B before integration.

## 4. Proposed Resolution Step Format

Each resolution step will follow this proposed structure:

```prolog
step(Sequence, Path, Depth, Action, Goal, Clause, RemainingGoals, Bindings).
```

### Fields

- `Sequence`: Chronological number of the recorded step.
- `Path`: Sequence of clause-choice positions identifying the explored alternative.
- `Depth`: Resolution depth at that step.
- `Action`: Type of resolution action.
- `Goal`: Selected logical goal.
- `Clause`: Fact or rule applied, when applicable.
- `RemainingGoals`: Goals remaining after the resolution step.
- `Bindings`: Current substitutions for query variables.

The `Path` field provides information about the alternatives explored by the resolution engine.

It is not a final tree-node identifier.

Part B will interpret the recorded steps and paths to construct the tree hierarchy, assign node identifiers, and establish parent-child relationships.

The representation of goals, clauses, paths, and bindings must be agreed upon before integration.

## 5. Proposed Resolution Actions

The engine may report the following actions:

| Action | Meaning |
|---|---|
| `start` | Resolution begins. |
| `apply` | An applicable clause is selected and applied. |
| `success` | All pending goals have been satisfied. |
| `failure` | A resolution branch cannot be satisfied. |
| `cutoff` | Resolution reaches the configured depth limit while goals remain unresolved. |
| `backtrack` | Resolution returns to explore another alternative. |

### Important Distinction

A failed branch and a depth-limited branch are not equivalent.

A `failure` indicates that the branch cannot satisfy its goals using the applicable alternatives.

A `cutoff` indicates that further expansion was prevented by the configured depth limit.

A depth-limited branch must not automatically be classified as logically false.

## 6. Variable Substitutions

Variable substitutions will be represented using stable values.

The proposed representation is:

```prolog
binding(VariableName, Value)
```

Example:

```prolog
binding("V1", "luis")
```

When original query variable names are unavailable, the engine may use consistent identifiers such as `V1`, `V2`, and `V3`.

The representation must preserve the association between each query variable and its corresponding value.

Previously recorded steps must not change when Prolog backtracks and explores another alternative.

The exact format for unbound variables, compound terms, and substitutions will be validated during implementation.

## 7. Supported Language Subset

The initial engine will support:

- Facts.
- Definite Horn-clause rules.
- Logical queries.
- Conjunctions of goals.
- Goal selection.
- Clause selection.
- Unification.
- Variable substitutions.
- Recursive rules.
- Backtracking.
- Multiple solutions.
- Failed queries.
- Configurable resolution depth.

The implementation will focus on a defined educational subset of Prolog.

It will use SWI-Prolog's logical mechanisms rather than implementing an independent Prolog simulator.

## 8. Scope Restrictions

The initial version will not support:

- Prolog cut (`!`).
- Dynamic database modification.
- Arbitrary built-in predicates.
- General negation-as-failure.
- Disjunction as a separate query construct.
- A complete implementation of the Prolog language.

The supported subset must remain consistent with the project scope approved by the instructor.

Additional features must not compromise the completion of the approved base functionality.

## 9. Resolution Behavior

The engine will follow the principles of SLD resolution.

### Goal Selection

The engine will use a leftmost goal-selection strategy.

For a conjunction of goals, the leftmost unresolved goal will be selected first.

### Clause Selection

The engine will search for applicable program clauses.

Applicable clauses will be considered in their defined order.

### Unification

The selected goal will be unified with the head of an applicable clause.

Successful unification may produce substitutions for logical variables.

### Resolvent Construction

When a clause is applied, its body goals will replace the selected goal.

The remaining goals will be preserved so that resolution can continue.

### Recursive Resolution

The engine will continue resolving goals recursively until the branch succeeds, fails, or reaches the configured depth limit.

### Successful Resolution

A branch succeeds when no unresolved goals remain.

### Failed Resolution

A branch fails when its selected goal cannot be satisfied using any applicable clause.

### Backtracking

When different applicable clauses exist, the engine will explore the corresponding alternatives.

Backtracking will allow the engine to discover multiple solutions.

### Depth Control

The engine will maintain a configurable depth limit.

If the limit is reached while unresolved goals remain, further expansion will stop and the branch will report a cutoff.

The engine must distinguish this situation from an ordinary logical failure.

## 10. Illustrative Example

Consider the following Prolog program:

```prolog
parent(ana, luis).
parent(ana, marta).
```

Example query:

```prolog
?- sld_trace(parent(ana, X), 5, Steps, Answers).
```

The expected logical solutions are:

```prolog
X = luis;
X = marta.
```

The engine should generate resolution information for both successful alternatives.

That information should include:

1. The initial query.
2. The goal selected for resolution.
3. The applicable facts.
4. The substitutions produced by unification.
5. The successful outcomes.
6. The exploration of the alternative clause.

Part B will use the resolution information to construct the corresponding SLD branches.

This example is illustrative.

The proposed interface has not yet been implemented or tested.

## 11. Integration Requirements

The following requirements must be respected:

1. Part A must not construct the final SLD tree.
2. Part A must not export the tree as JSON.
3. Part B must not reimplement the logical resolution engine.
4. Part B must construct the tree using information produced by Part A.
5. Part C must visualize the JSON generated by Part B.
6. Previously recorded information must remain stable during backtracking.
7. The integration must distinguish successful, failed, and depth-limited branches.
8. Multiple solutions must be represented without losing their corresponding resolution alternatives.
9. The components must follow an agreed data contract.
10. Each component must remain independently testable.
